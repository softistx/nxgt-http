A new `scalars` option, `'pattern' | 'exact'` (default `'pattern'`, as before). With `scalars: 'exact'`, a string or numeric scalar of `@nxgt/typespec` (a schema with `x-nxgt-scalar`) is validated by its own schema from `@nxgt/zod`, such as `ibanSchema`, imported by name, instead of `z.string().regex(...)`; the spec's own `pattern` is kept on top as `.check(z.regex(...))`, so a scalar narrowed in the spec stays narrow, and a `minLength` or `maxLength` it adds is kept as `.check(z.maxLength(n, message))`. `@nxgt/zod` `^0.1.3` is an optional peer, needed only by the generated code. A numeric scalar (`Port`, `Latitude`, `PositiveInt`, `SafeInt`…) is its `@nxgt/zod` schema (`portSchema`), with a bound of the spec that the schema does not already enforce, and `multipleOf`, kept on top as `.check(z.lte(n, message))`; the integer scalars refuse `-0`, which `'pattern'` accepts. The codecs (`DateTime`, `Timestamp`, `BigInt`, `Long`) keep their pattern. A new `unknown_scalar` warning reports an `x-nxgt-scalar` that `@nxgt/typespec` does not declare, on a string or a number. The README and the guides document it: the `@nxgt/zod` peer, a copy-paste example, and troubleshooting entries for a missing `@nxgt/zod`, an `unknown_scalar` warning and a `zod` older than 4.6.5.
